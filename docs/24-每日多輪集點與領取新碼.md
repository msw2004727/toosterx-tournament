# 每日多輪集點與領取新碼

## 確認規則與資料模型

每日第一輪沿用原卡號；每輪完成當日開放攤位後取得一張抽獎資格，使用者自行按「代建新卡（領新碼進入下一輪）」才建立下一輪。輪次不設上限。每輪集點下方標示本輪碼號，QR 與複製代號指向今天最新輪。舊輪保留展示，未滿最新輪按當下開攤狀態計算。攤位由四攤改回五攤時，已確認完成的四攤輪保留資格，新的第五攤集點只進最新輪；作廢紀錄仍會撤回不再成立的資格。

同一 LINE 帳號仍只有一個 users.gamePassId／canonical playerId；新碼是服務端保留的 players 別名文件（roundAliasOf、roundDate、roundNumber），不新增參與者或改變聯絡資料。所有原始成績仍使用 canonical playerId，新增 roundCode。舊紀錄沒有 roundCode 時歸第一輪。players.challengeRounds[date] 持久化輪次與已滿攤位快照。attemptPublic 只增加公開 roundCode，保留既有敏感欄位白名單限制。

## 施工階段、步驟與做法

1. 在獨立工作樹以已發布攤位完整性修補為基底；與另一對話協調 UI 所有权，合併最新 demo 籤表，禁止回退其他功能。
2. 純引擎按日期、碼號分配紀錄；完成後凍結 required 集合。開關攤位交易寫入 challengeRoundHistory，使用入庫時間保留在 trigger 延遲時已完成的資格。
3. 領碼 callable 驗證非匿名登入、帳號卡主、活動當日、有效集滿及 predecessor code；FireStore 交易保留唯一新碼並寫稽核。同一前輪重試／並發均返回同一新碼。
4. Firestore rules 強制只能對 canonical player 的當日最新碼登錄；普通使用者不能改輪次或製造別名。攤位掃碼解析別名，在人物本體登錄並記錄本輪碼。
5. 我的挑戰卡與挑戰首頁共用輪次元件，集滿／伺服器確認／卡主／當日／在線時開按鈕。按後新增空白下一輪；離線、未確認、訪客、歷史日期、配號中均停用。
6. 抽獎及完整名單匯出按 canonical 玩家彙總各輪張數，保留 UID、聯絡、零分、入庫／參與時間；增加輪次碼及明細單筆碼號。

## 驗收

- 引擎：四改五保留；未滿跟隨開攤；新點只进最新輪；重複不加券；跨日獨立；作廢撤回；延遲 trigger 資格保留；持久化白名單。
- Functions Emulator：未滿／他人／錯日拒絕；兩個並發呼叫只建一張新碼；连续第三輪；UID、聯絡、排行身分保留；抽獎與完整匯出一致；公開投影保留碼且隱藏敏感資料。
- Rules Emulator：當前碼可寫；舊码、漏码、偽碼、別名人物拒絕；普通用戶不能自行增加資格／輪次。
- 瀏覽器：手機、桌機、320px 下按鈕反灰→完成→領碼→第二輪→再完成→第三輪；所有輪次碼號、最新 QR、首頁即時更新；重開第五攤；歷史日期／離線；攤位新碼寫入與舊碼拒絕。
- 對以上关键規則執行定向變異；正常基線先通過，預期斷言抓到錯誤後來源完整還原；執行既有 unit／挑戰、攤位、匯出與完整性 regression。
- Demo 雲端實際 callable、rules、身份與資料投影驗收，正式站版本／來源與設定核對。

## 佈署步驟

1. 從 origin 重新取得 main／demo，整合協調完成的 UI 與籤表；檢查 mutation guard、anchors、版本一致，固定候選 SHA，完整驗收後才發布。
2. 先發布 Demo 相關 Functions 與 rules；前端推送 demo 由 Cloudflare 發布，核對線上新版。執行 scripts/release-challenge-rounds.mjs --project feda-cup-demo --apply，備份至 ignored tools，再啟用設定並重算 canonical 玩家，不寫原始成績／聯絡／UID。
3. 完成 Demo 雲端實測並清除專屬 QA 活動後，將同一候選 fast-forward main。發布正式 Functions／rules、核對 cup.toosterx.com 版本，再對 feda-cup-2026 啟用同一設定和重算。核對 raw attempts、UID映射、聯絡資料未被修改，以及抽獎彙總相符。
4. 記錄版本、SHA、Functions ACTIVE、Cloudflare 部署、測試數與資料核對摘要，回報兩個協調對話。

## 回復

先設 config/challengeRewards.nextCardEnabled=false 暫停新碼，保留 roundsEnabled=true，既有最新碼、成績、資格與快照仍有效。已經發碼後不能直接關閉多輪或回退舊 rules，否则舊卡會重新可寫而新碼失效；須保留新碼解析與安全 rules，修正問題再開領碼。備份只作稽核，不能用舊快照覆寫发布後新增資料。尚未發任何新碼時才可回到基底前端與設定。所有資料操作僅用明確活動 ID，QA 清理不得触碰正式活動。
