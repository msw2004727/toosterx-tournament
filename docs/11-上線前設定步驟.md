## 1. 兩組 LIFF Channel（最急，而且有一步不可逆）

### ⚠️ 先讀這段再動手

LINE 的 **userId 是「每個 Provider 一組」發的，不是每個 Channel 一組**。
同一個人在不同 Provider 底下會拿到**完全不同的 userId**。

我們整個身分設計建立在「飛達盃的 uid 跟 FC-Football 的 uid 是同一個」上面
（`teams/{id}.captainUid` 與 FC 的 `users/{uid}` 是同一把鍵）。所以：

> **LIFF Channel 必須建在 FC-Football 所屬的那個 Provider 底下。**
> 另外開一個 Provider，等球隊開始報名之後才發現，錯的 ID 已經寫進資料裡，
> 只能整個重來。

這是唯一一步做錯就要重做的。其他都能改。

### 步驟

**① 找出 FC-Football 在哪個 Provider**

1. 開 <https://developers.line.biz/console/>，用你管理 FC-Football 的 LINE 帳號登入
2. 首頁會列出你所有的 **Provider**（像資料夾）
3. 一個一個點進去，找到裡面有 FC-Football 那個 Channel 的那一個
4. **把這個 Provider 的名字記下來**。接下來兩個 Channel 都建在它底下

> 找不到的話，從 FC-Football 的 Firebase 專案回推：
> Firebase Console → Authentication → Sign-in method → 看有沒有設定 LINE，
> 或問當初建 FC 的人。**不確定就先不要建**，寧可多花半天問清楚。

**② 在那個 Provider 底下建立第一個 Channel（正式站用）**

1. 點進那個 Provider → 右上 **Create a new channel**
2. 選 **LINE Login**（不是 Messaging API）
3. 填：
   - Channel name：`FEDA CUP 2026`
   - Channel description：隨意
   - App types：勾 **Web app**
4. 建立完成

**③ 在這個 Channel 裡建立 LIFF App**

1. 進入剛建好的 Channel → 上方分頁選 **LIFF**
2. 點 **Add**
3. 填：
   - LIFF app name：`FEDA CUP`
   - Size：**Full**
   - Endpoint URL：`https://cup.toosterx.com`
   - Scopes：勾 **profile** 與 **openid**（兩個都要，缺一個就拿不到 userId 或驗不了 token）
   - Bot link feature：**Off**
4. 建立後會得到一組 **LIFF ID**，長得像 `2000123456-AbCdEfGh`

**④ 重複 ②③ 建第二個，給 demo 站用**

- Channel name：`FEDA CUP 2026 Demo`
- Endpoint URL：`https://cup-demo.toosterx.com`
- 其餘相同
- **一樣要建在同一個 Provider 底下**

**⑤ 把四個值交給我**

在每個 Channel 的 **Basic settings** 分頁可以看到 Channel ID 與 Channel secret：

| 要交的東西 | 哪裡拿 | 可以貼在對話裡嗎 |
|---|---|---|
| 正式站 LIFF ID | LIFF 分頁 | ✅ 可以（公開值，會出現在前端） |
| Demo 站 LIFF ID | LIFF 分頁 | ✅ 可以 |
| 正式站 Channel ID | Basic settings | ✅ 可以（公開值） |
| Demo 站 Channel ID | Basic settings | ✅ 可以 |
| **Channel secret ×2** | Basic settings | ❌ **不要貼**，見下方 |

**Channel secret 你自己設定，不要給任何人（包括我）**——R-SEC-001。
在專案目錄下執行這兩行，它會提示你貼上，貼上的內容不會留在畫面或指令歷史裡：

```bash
npx firebase functions:secrets:set LINE_CHANNEL_SECRET --project demo
```


### 1.5 ⚠️ 一個必須授權的 IAM 權限（否則第一次登入就會失敗）

**這一項一定要做，而且只有你能做**（IAM 是安全設定，我不代勞）。

`lineLogin` 最後一步要發 Firebase custom token。在 Cloud Functions 上，
那是透過 IAM Credentials 的 `signBlob` 簽出來的，需要 Function 的執行身分
對**它自己**有 `iam.serviceAccounts.signBlob` 權限。

預設的執行身分（compute 服務帳戶）只有 `roles/editor`，而
**editor 不含 signBlob**——已用下面這行實測確認：

```bash
gcloud iam roles describe roles/editor --format="value(includedPermissions)" | grep -o signBlob
```

（沒有輸出＝不含）

**症狀很難查**：部署會成功、函式探索會成功、假 token 也會得到正確的錯誤訊息，
只有真的有人用 LINE 登入時才會炸，而且錯誤是
`Permission 'iam.serviceAccounts.signBlob' denied`。

#### Demo（✅ 已完成 2026-09-02）

```bash
gcloud iam service-accounts add-iam-policy-binding 479711861820-compute@developer.gserviceaccount.com --member="serviceAccount:479711861820-compute@developer.gserviceaccount.com" --role="roles/iam.serviceAccountTokenCreator" --project=feda-cup-demo
```

> 看起來像「自己授權給自己」，那是對的：Google 的簽章 API 要求呼叫者對
> 目標服務帳戶有權限，而這裡的呼叫者與目標是同一個帳戶。

#### 正式站：⚠️ **必須等第一次部署 Functions 之後才做得了**

現在對正式站跑同一行會得到：

```
ERROR: NOT_FOUND: Unknown service account
```

**這不是打錯字，是順序問題。** `{專案編號}-compute@developer.gserviceaccount.com`
這個預設服務帳戶是在專案第一次用到 Compute Engine（部署 Cloud Functions 就會用到）
時才由 Google 建立的。正式站從來沒部署過 Functions，所以它還不存在——
實測 `feda-cup-2026` 目前只有一個 `firebase-adminsdk-fbsvc@…`。

所以正式站的授權**排進 §5 上線流程的第 4 步**（部署完 Functions 之後），
不要現在做。到時候的指令是：

```bash
gcloud iam service-accounts add-iam-policy-binding 223092701593-compute@developer.gserviceaccount.com --member="serviceAccount:223092701593-compute@developer.gserviceaccount.com" --role="roles/iam.serviceAccountTokenCreator" --project=feda-cup-2026
```

#### 或者用網頁後台

1. 開 <https://console.cloud.google.com/iam-admin/serviceaccounts?project=feda-cup-demo>
2. 點 `479711861820-compute@developer.gserviceaccount.com`
3. 上方分頁選 **權限（PERMISSIONS）**
4. 點 **授予存取權（GRANT ACCESS）**
5. 新增主體貼上：`479711861820-compute@developer.gserviceaccount.com`（同一個）
6. 角色選 **服務帳戶權杖建立者（Service Account Token Creator）**
7. 儲存
8. 正式站重複一次，網址把 `feda-cup-demo` 換成 `feda-cup-2026`、
   帳戶換成 `223092701593-compute@developer.gserviceaccount.com`

#### 怎麼確認做對了

```bash
gcloud iam service-accounts get-iam-policy 479711861820-compute@developer.gserviceaccount.com --project=feda-cup-demo
```

要看到 `roles/iam.serviceAccountTokenCreator` 這一條。授權後大約一分鐘生效。

## 2. 報名開關（demo 已設定 ✅）

Demo 站目前：

| 欄位 | 值 |
|---|---|
| `open` | `true` |
| `opensAt` | 2026/9/2 16:11（即刻） |
| `closesAt` | **2026/9/13 00:00**（主辦 2026-09-03 指定） |

> 📌 **9/13 00:00 的意思是「9/12 整天都還能報，一過午夜就關」**，
> 不是「9/13 整天都能報」。要讓 9/13 也能報名的話是 `2026-09-14T00:00`。
>
> 這樣排的時間很充裕：離開賽（10/9）有 26 天，離彩排（10/6–10/7）有 23 天，
> 中間可以從容做完審核報名、排種子序、產生賽程、印檢錄表。

改截止日不用進 Console，跑這一行就好（時間一律填台北時間）：

```bash
node scripts/set-registration.mjs --project feda-cup-demo --closes 2026-09-13T00:00
```

其他用法：`--show` 看現況、`--open` / `--close` 開關報名、`--clear-closes` 取消截止。

> ⚠️ **不要在 Console 手動填 `closesAt`。** 它必須是 Timestamp 型別；
> 在 Console 用字串填，rules 的 `request.time <= closesAt` 會直接判偽，
> 報名會**安靜地永遠打不開**，畫面上看起來卻一切正常。

正式站的 `config/registration` 在上線時一併建立（見 §5）。

## 3. Cloudflare Browser Cache TTL（✅ 已完成）

實測（2026-09-02，帶隨機 query 強制回源）：

```
cup-demo.toosterx.com  /js/firebase-config.js  public, max-age=0, must-revalidate, no-cache
cup.toosterx.com       /js/firebase-config.js  public, max-age=0, must-revalidate
```

兩個網域都回我們自己在 `_headers` 寫的值，zone 不再改寫。R-REL-015 生效。
（正式站少一個 `no-cache` 是正常的：`main` 還停在舊版的 `_headers`。）

### 這條規則為什麼存在——設定改好之前剛好親眼看到一次

M4-b 部署後，瀏覽器拿到的是**新的 `js/core/liff.js` 配舊的 `js/firebase-config.js`**：

```
SyntaxError: The requested module '../firebase-config.js'
             does not provide an export named 'LIFF'
```

伺服器上兩個檔案都是新的，壞的是那份還沒過期的 4 小時瀏覽器快取。
整頁載入失敗，而且對已經來過的訪客會持續到快取到期為止。

`app.js` 靜態 import 的三個模組（`firebase-config.js`、`config.js`、`theme.js`）
帶不了版號——沒有打包工具，動態 import 的網址才加得上 `?v=`。
所以這一層只能靠 HTTP 標頭守，這也是 `_headers` 存在的全部理由。

## 4. Functions 映像檔清理政策

### 這是什麼、為什麼要做

每次部署 Cloud Functions，Google 都會把程式打包成一個「容器映像檔」存起來。
**不清的話會一直累積**，每個月產生一點點儲存費用（金額很小，但沒有理由留著）。

設定「清理政策」＝告訴 Google「超過 N 天的舊映像檔就自動刪掉」。
保留幾天是為了萬一要退回舊版本，**建議留 3 天**。

### ⚠️ 一個很容易踩到的地方

指令有一個 `--location`（地區）參數，**預設是 `us-central1`（美國）**，
但我們的 Functions 建在 `asia-east1`（台灣）。
不指定地區的話，政策會設在一個我們根本沒用的地區，等於白做。

所以下面的指令**一定要帶 `--location asia-east1`**。

### 一步一步

**① 開啟終端機**

在 VS Code 裡按 <kbd>Ctrl</kbd> + <kbd>`</kbd>（Esc 下面那個鍵），
下方會跳出一個可以打字的黑色區塊。

確認左邊顯示的路徑是 `D:\kere\Documents	oosterx-tournament`。
不是的話先打這一行再按 Enter：

```bash
cd D:\kere\Documents	oosterx-tournament
```

**② 貼上這一行，按 Enter**

```bash
npx firebase functions:artifacts:setpolicy --project demo --location asia-east1 --days 3 -f
```

拆開來看：

| 這一段 | 意思 |
|---|---|
| `npx firebase` | 執行 Firebase 的工具 |
| `functions:artifacts:setpolicy` | 設定映像檔清理政策 |
| `--project demo` | 對 demo 專案做（`feda-cup-demo`） |
| `--location asia-east1` | **地區要指定**，見上面的警告 |
| `--days 3` | 保留 3 天，超過就刪 |
| `-f` | 不要問我，直接做（不然它會跳問題等你回答） |

**③ 你會看到什麼**

跑幾秒之後，最後一行大概會是這樣（文字可能略有不同）：

```
+  functions: Cleanup policy set for asia-east1
```

看到 `+` 或 `successfully` 就是成功了。

**④ 正式站現在還不用做**

正式站還沒部署過 Functions，也就還沒有映像檔。
等 §5 上線流程跑完之後再做一次，指令一樣，只要把 `demo` 換成 `prod`：

```bash
npx firebase functions:artifacts:setpolicy --project prod --location asia-east1 --days 3 -f
```

### 怎麼確認做對了

下次部署 Functions 時，**不會再出現**這一行警告就是成功了：

```
! functions: No cleanup policy detected for repositories in asia-east1.
```

### 如果出現錯誤

| 訊息 | 意思 | 怎麼辦 |
|---|---|---|
| `command not found: npx` | 這台電腦沒有 Node.js | 先裝 Node.js 22 |
| `Failed to authenticate` | Firebase 沒登入 | 先跑 `npx firebase login` |
| `Permission denied` | 帳號權限不足 | 確認登入的是 msw741121@gmail.com |

> 我沒有代勞這一項：它會**刪除**你專案裡的東西，而且是計費資源，
> 這種操作應該由你自己按下去。

## 5. 正式站上線

**還不要做。** 正式站 `main` 目前停在 M3b，Functions 也還沒部署。
流程是（R-GIT-001，方向不可反）：

```
demo 驗過  →  merge 進 main  →  部署正式站
```

等你在 <https://cup-demo.toosterx.com> 把賽務端與公開端都走過一遍、
確認沒問題之後跟我說，我會：

1. `git checkout main && git merge demo && git push`
2. `npm run deploy:rules:prod`
3. `npm run deploy:fn:prod`
4. **這時候 `223092701593-compute@…` 服務帳戶才會被建立出來**，
   接著才做得了 §1.5 的正式站授權（`signBlob`）。順序不能反。
5. 建立正式站的 `config/liff`（Channel ID `2011382367`）與 `config/registration`
6. 灌正式資料（**不是種子資料**——R-SEED-001 明訂 `scripts/seed.js` 只能對
   ID 含 "demo" 的專案執行，正式庫一律走管理後台匯入）
7. 逐項驗證並回報
