# 02｜賽制引擎與排名規則

> 這是整個系統的心臟。原則只有一條：**賽制不寫死在程式碼裡，一律以設定檔驅動。**
> 程式碼中不得出現 `if (divisionId === 'women')` 這類判斷。

---

## 1. 領域模型

```
Event（活動）
 └── Division（組別）        ← 綁定一個 Format 與一個 RankingRule
      └── Stage（階段）      ← roundRobin / knockout / placement
           ├── Group（小組）  ← 僅 roundRobin 有
           └── Match（場次）
                └── Timeline（事件）
      Standing（積分榜）      ← 依 Stage × Group 計算
      FinalRanking（最終排名）← 依 Format 的 finalRankingMap 解算
```

### 1.1 核心流程

```
① 建立 Division（選 Format）
      ↓
② 匯入／建立 Team，指派小組（自動蛇形或手動）
      ↓
③ generateSchedule()  ← 依 Format 產生所有 Stage 的 Match
      ↓（排名階段的 Match 先以 placeholder 產生，觀眾看得到「A組第1名 vs B組第2名」）
④ 現場輸入 Score
      ↓
⑤ recalcStanding()    ← 觸發式重算積分榜
      ↓
⑥ resolveAdvancement() ← 前一階段完成時，把 placeholder 換成實際隊伍
      ↓
⑦ computeFinalRanking() ← 全部完賽後解算 1–N 名
```

## 2. Format 設定檔

存放於 `config/formats`。一個 Format 描述「N 隊要怎麼比」，與組別名稱無關，可跨賽事重用。

### 2.1 Schema

```ts
type Format = {
  formatId: string
  name: string
  teamCount: number
  description: string
  stages: Stage[]
  finalRankingMap: RankSource[]
}

type Stage = {
  stageId: string
  name: string
  type: 'roundRobin' | 'knockout'
  order: number

  // roundRobin 專用
  groupCount?: number
  groupSize?: number
  legs?: 1 | 2                      // 單／雙循環
  seedingMethod?: 'snake' | 'manual' | 'random'

  // knockout 專用
  slots?: Slot[]
  thirdPlaceMatch?: boolean
  drawRule?: 'none' | 'penalty' | 'goldenGoal'   // 平手處理
}

type Slot = {
  matchKey: string                  // 該 Format 內唯一
  label: string                     // 顯示名稱，如「準決賽①」
  home: TeamSource
  away: TeamSource
  round?: number
}

type TeamSource =
  | { type: 'standing', stageId: string, groupId: string, rank: number }
  | { type: 'matchWinner', matchKey: string }
  | { type: 'matchLoser',  matchKey: string }
  | { type: 'fixed', teamId: string }

type RankSource = {
  rank: number
  from: TeamSource
}
```

### 2.2 平手處理（knockout 階段）

| drawRule | 行為 |
|---|---|
| `none` | 允許平手，名次由 RankingRule 的 `manual` 落到 Admin 裁定 |
| `penalty` | 90 分鐘平手直接 PK 大戰，記入 `penaltyScore`；正規比分仍記平手 |
| `goldenGoal` | 進入延長，先進球者勝 |

> **建議**：兒童組與女子組用 `penalty`（避免拖時間）；成人組用 `penalty`。
> 排名賽（5–8 名）平手可設 `none` 由主辦裁定，加快節奏。

## 4. 循環賽程產生演算法

採 **circle method（Berger 輪轉表）**，可保證每隊每輪最多一場、主客場大致平衡。

### 4.1 演算法

```js
// 回傳 rounds: Array<Array<[homeIdx, awayIdx]>>
function berger(n) {
  const teams = [...Array(n).keys()];
  if (n % 2 === 1) teams.push(-1);          // -1 = 輪空（bye）
  const m = teams.length;
  const rounds = [];
  for (let r = 0; r < m - 1; r++) {
    const pairs = [];
    for (let i = 0; i < m / 2; i++) {
      const a = teams[i], b = teams[m - 1 - i];
      if (a === -1 || b === -1) continue;    // 輪空不排場
      // 交錯主客，讓主場次數平均
      pairs.push(r % 2 === 0 ? [a, b] : [b, a]);
    }
    rounds.push(pairs);
    // 固定第 0 位，其餘順時針輪轉
    teams.splice(1, 0, teams.pop());
  }
  return rounds;
}
```

### 4.2 產生結果驗證

**3 隊（U6 A 組）** → `berger(3)`：

| 輪次 | 對戰 |
|---|---|
| R1 | A1 vs A2 |
| R2 | A3 vs A1 |
| R3 | A2 vs A3 |

每隊 2 場 ✅（企劃書列的 A1vsA2 / A2vsA3 / A1vsA3 為相同組合，僅主客與順序差異）

**4 隊（成人 A 組）** → `berger(4)`：

| 輪次 | 對戰 |
|---|---|
| R1 | A1 vs A4、A2 vs A3 |
| R2 | A3 vs A1、A4 vs A2 |
| R3 | A1 vs A2、A3 vs A4 |

✅ 與企劃書第六章列出的順序完全一致。

**4 隊女子組（單一組）** 同上，共 6 場。

### 4.3 分組（Seeding）

`seedingMethod: 'snake'` 蛇形分組：依 `team.seed` 由小到大分派。

```
seed:  1  2  3  4  5  6  7  8
組別:  A  B  B  A  A  B  B  A
```

未設 seed 時退回報名順序；Admin 可在後台**手動拖曳調整分組**（`seedingMethod:'manual'`）。

### 4.4 賽程時間排定

產生對戰後，另一支排程器把場次分配到場地與時段：

```js
scheduleMatches({
  matches,                 // 已產生的對戰
  venues: ['venue-a','venue-b','venue-c'],
  dayStart: '2026-10-11T08:30:00+08:00',
  matchDurationMin: 30,
  bufferMin: 10,           // 換場緩衝
  minRestMin: 30,          // 同隊兩場之間最短休息
  lunchBreak: { from:'12:00', to:'13:00' }
})
```

**限制條件**（軟性，違反時給警示不阻擋）：

1. 同一隊不得在同一時段有兩場（硬性，阻擋）
2. 同一隊連續兩場之間至少 `minRestMin`（軟性，警示）
3. 同階段的最後一輪盡量同時開賽（避免「算分」爭議）——4 隊組建議最後一輪同時開球
4. 決賽排在最後時段

> **MVP 做法**：排程器產生初稿後，**Admin 可在後台以拖曳方式手動微調**時間與場地。不追求全自動最佳化。

## 5. 積分與積分榜計算

### 5.1 積分規則

```js
points: { win: 3, draw: 1, loss: 0 }
```

### 5.2 棄賽／未到（Walkover）

```js
walkover: {
  scoreFor: 3, scoreAgainst: 0,     // 判定比分 3:0
  awardPoints: 3,                   // 勝隊得分
  penaltyPoints: 0,                 // 棄賽隊得分
  countInGoalStats: true            // 是否計入得失球（可設定）
}
```

**整隊退賽（withdrawn）**的處理選項（Division 層設定）：

| 選項 | 行為 |
|---|---|
| `voidAll`（建議） | 該隊所有場次成績作廢，其他隊之間的成績不受影響（FIFA 通用做法） |
| `keepAsWalkover` | 已賽場次保留，未賽場次判 3:0 |

### 5.3 積分榜欄位

| 欄位 | 代碼 | 說明 |
|---|---|---|
| 賽 | `played` | 已完賽場次 |
| 勝 | `win` | |
| 和 | `draw` | |
| 負 | `loss` | |
| 進 | `goalsFor` | |
| 失 | `goalsAgainst` | |
| 差 | `goalDiff` | `goalsFor - goalsAgainst` |
| 積分 | `points` | |
| 行為分 | `fairPlayPoints` | 見 §6.3 |

### 5.4 重算時機

`recalcStanding` 由 `onDocumentWritten('events/{e}/matches/{m}')` 觸發，條件：

- `status` 變為 `finished` / `confirmed` / `walkover`
- `score` 有變動
- `result` 有變動

重算範圍：該 match 所屬的 `divisionId + stageId + groupId` 一份 standing。

> **注意**：Function 必須具備冪等性。以 `standing.version` 遞增並在寫入時比較，避免亂序覆寫。

## 6. RankingRule｜同分排序規則

存放於 `config/rankingRules`。

### 6.1 Schema

```ts
type RankingRule = {
  rankingRuleId: string
  name: string
  points: { win: number, draw: number, loss: number }
  criteria: Criterion[]        // 依序套用，直到分出高下
  fairPlay: FairPlayConfig
}

type Criterion =
  | 'points'                   // 積分（一律第一）
  | 'headToHeadPoints'         // 對戰積分
  | 'headToHeadGoalDiff'       // 對戰得失球差
  | 'headToHeadGoalsFor'       // 對戰進球
  | 'headToHeadWins'           // 對戰勝場
  | 'goalDiff'                 // 全組得失球差
  | 'goalsFor'                 // 全組進球
  | 'goalsAgainstAsc'          // 全組失球少者優先
  | 'wins'                     // 勝場多者
  | 'fairPlay'                 // 行為分高者（罰分少者）
  | 'seed'                     // 種子序
  | 'drawLots'                 // 抽籤（系統產生隨機但可稽核的序）
  | 'manual'                   // 主辦裁定（永遠放最後）
```

### 6.2 本次採用的規則

**`RR_FEDA_DEFAULT`（企劃書版．預設）**

```js
{
  rankingRuleId: 'RR_FEDA_DEFAULT',
  name: '飛達盃預設（對戰關係優先）',
  points: { win: 3, draw: 1, loss: 0 },
  criteria: [
    'points',
    'headToHeadPoints',
    'headToHeadGoalDiff',
    'headToHeadGoalsFor',
    'goalDiff',
    'goalsFor',
    'goalsAgainstAsc',
    'fairPlay',
    'manual'
  ],
  fairPlay: { yellow: -1, secondYellow: -3, directRed: -4, yellowThenRed: -5 }
}
```

對應企劃書第七章的「對戰勝負關係 → 得失球差 → 總進球數 → 失球數較少 → 紅黃牌 → 主辦處理」，只是把「對戰關係」展開成三層（積分／得失球差／進球），這是國際通行的展開方式。

**`RR_FEDA_YOUTH`（兒童組）**

兒童組建議**移除行為分**、並在對戰關係之後就落到主辦裁定，避免用得失球差鼓勵大比分：

```js
criteria: ['points','headToHeadPoints','headToHeadGoalDiff','goalDiff','goalsFor','manual']
```

> 另建議兒童組開啟 **`mercyRule`（仁慈規則）**：分差達 7 球時比分不再顯示於公開端（顯示為「7+」），且得失球差最多計 7。設定：
>
> **實作語意（M2 定案）**：只壓 `goalDiff` 的**每場**貢獻（15:0 → 計 +7／−7；兩場 15:0 與 9:0 是 +7 +7 = +14，不是總和封頂）。
> `goalsFor` / `goalsAgainst` **照實記錄**，因為規格只說「得失球差」最多計 7。
> `cap` 小於 1 會被強制拉回 1，避免後台把 cap 打成 0 導致勝場變平手。
>
> ⚠️ **待主辦確認**：如此一來 `RR_FEDA_YOUTH` 的 `goalsFor` 這一層仍會讓 15:0 勝過 8:0，
> 仁慈規則沒有完全消除「灌球有利」的誘因。若要徹底消除，應改為
> 「進球數也一併封頂」或「兒童組移除 `goalsFor` 條件」。見 `00 §待決事項`。
> ```js
> divisions.u6.display = { mercyRule: { enabled: true, cap: 7 } }
> ```

```js
  'points',
  'headToHeadPoints','headToHeadGoalDiff','headToHeadGoalsFor',
  'goalDiff','goalsFor',
  'fairPlay','drawLots'
]
```

依 FIFA 2026 世界盃規則：先比對戰（積分、得失球差、進球），再比全組（得失球差、進球），再行為分，最後不抽籤而用世界排名——基層賽事以 `drawLots` 或 `manual` 取代。

### 6.3 行為分（Fair Play Points）

採 FIFA 標準罰分制，**分數越高越好**（實際為負值，罰分越少越接近 0）：

| 事件 | 罰分 |
|---|---|
| 黃牌 | −1 |
| 兩黃換紅 | −3 |
| 直接紅牌 | −4 |
| 黃牌後直接紅牌 | −5 |

同一名球員在同一場：若拿到第二張黃牌，只計 −3（不再另計那張黃牌的 −1）。

**如何判斷 −4 與 −5**：`timeline` 的 `cardType` 只有 `yellow` / `second_yellow` / `red` 三種值（裁判端也只提供這三個選項）。行為分在完賽時由 Function 計算，規則是：

```
掃描該球員在該場所有未作廢的 card 事件
  ├─ 只有 red，且此前沒有 yellow            → directRed   (−4)
  ├─ 有 red，且此前已有未作廢的 yellow       → yellowThenRed (−5)
  ├─ second_yellow                          → −3（該球員本場黃牌不再另計）
  └─ 其餘 yellow                             → 每張 −1
```

也就是說裁判不需要判斷「這是不是黃牌後的紅牌」，系統自己從事件序推算。

### 6.4 對戰關係（Head-to-Head）的正確算法

⚠️ 這是最容易寫錯的地方。正確流程：

```
1. 先依 points 分組出「同分群」（tied group）
2. 若同分群只有 2 隊 → 直接比兩隊之間那 1 場（或 2 場）
3. 若同分群 ≥ 3 隊 →
   3.1 只取「同分群成員彼此之間」的比賽，建立迷你積分表
   3.2 依 headToHeadPoints → headToHeadGoalDiff → headToHeadGoalsFor 排序
   3.3 若迷你表把群拆成更小的子群，對每個子群「從步驟 1 重新開始」（遞迴）
   3.4 若迷你表完全分不出，才落到 goalDiff 等全組指標
4. 全部條件用完仍同分 → hasUnresolvedTie = true，Admin 手動指定
```

**必須注意的陷阱**：當 3 隊同分，經對戰關係拆出「1 隊領先、2 隊仍同分」時，**剩下 2 隊要重新只比彼此那一場**，不能沿用 3 隊迷你表的數字。這點在單元測試中必須有專門案例。

### 6.5 排序追蹤（tieBreakTrace）

每一列 standing 記錄實際用到哪一層才分出高下：

```js
tieBreakTrace: ['pts=7', 'h2h-pts=3(vs t-102)', 'decided@headToHeadPoints']
```

用途：現場有人質疑名次時，Admin 可以直接秀出判定依據，不必翻規程。這是基層賽事**極高價值**的功能。

## 7. 晉級解算（Advancement）

### 7.1 觸發條件

`resolveAdvancement(divisionId, stageId)` 在下列時機執行：

- 某 Stage 的所有 Match 皆 `finished` 或 `confirmed`
- 且該 Stage 的 standing `hasUnresolvedTie === false`
- 且 Admin 未鎖定（`stage.manualHold !== true`）

### 7.2 解算步驟

```
1. 讀取 Format 中下一個 Stage 的 slots
2. 對每個 slot 的 home / away TeamSource 求值：
   - standing  → 讀 standings/{div}__{stage}__{group}.rows[rank-1].teamId
   - matchWinner → 讀該 matchKey 的 result.winner 對應 teamId
   - matchLoser  → 同上取反
3. 將 teamId、隊名、abbr、logoUrl 寫入對應 match 的 home/away
4. 清除 placeholder，match.status: scheduled → ready
5. 寫入 audit（action: 'advancement.resolve'）
6. stage.advancementResolved = true
```

### 7.3 人工介入

Admin 可以：

- **鎖定自動晉級**（`manualHold`）：現場臨時改制時避免系統亂填
- **直接指定晉級隊伍**：覆寫 match.home/away，記錄 audit
- **重跑晉級**：清除後重新解算（需二次確認，因為下游可能已有比分）

> 若下游 match 已有比分，重跑晉級必須阻擋，改為「先清除比分」才允許。

## 9. 狀態機

### 9.1 Match 狀態機

```
scheduled ──(檢錄開始)──► checkin ──(雙方名單確認)──► ready
                                                        │
                                                    (開賽)
                                                        ▼
   ┌──────────────────── live ◄──(繼續)── halftime ◄──(中場)──┐
   │                      │                                    │
   │                  (完賽送出)                                │
   │                      ▼                                    │
   │                  finished ──(覆核)──► confirmed            │
   │                      │                                    │
   └──(Admin 退回)────────┘                                    │
                                                               │
   任一狀態 ──(Admin)──► postponed / cancelled / walkover ──────┘
```

| 狀態 | 說明 | 誰可轉換 |
|---|---|---|
| `scheduled` | 已排定 | 系統 |
| `checkin` | 檢錄中 | 賽務 |
| `ready` | 名單確認，可開賽 | 賽務 |
| `live` | 進行中 | 裁判 |
| `halftime` | 中場 | 裁判 |
| `finished` | 已完賽（比分鎖定） | 裁判 |
| `confirmed` | 場地主任／管理員覆核 | 場地主任／Admin |
| `postponed` | 延期 | Admin |
| `cancelled` | 取消 | Admin |
| `walkover` | 一方棄賽 | Admin |

**規則**：

- `finished` 之後 `lock.locked = true`，一般賽務不可再改
- 只有 Admin 可從 `finished`／`confirmed` 退回 `live`，且必須填 `reason`（場地主任沒有此權限）
- `finished → confirmed` 由場地主任或 Admin 覆核；一般賽務在完賽當下已被 `lock` 鎖定，無法再寫入
- `confirmed` 才會納入「官方成績」匯出；`finished` 已可觸發積分重算（現場即時性優先）

### 9.2 Stage 狀態機

```
pending ──(首場開賽)──► live ──(全部完賽)──► finished ──(晉級解算)──► resolved
```

### 9.3 Division 狀態機

```
scheduled ──► live ──► finished ──(發布最終排名)──► published
```

## 10. 特殊情況處理對照表

| 情況 | 系統行為 | 需要誰 |
|---|---|---|
| 比分輸錯，已完賽 | Admin 解鎖 → 改分 → 自動重算 standing → 若已解算晉級則警示 | Admin |
| 球隊臨時棄賽（單場） | 設 `status='walkover'` + `walkoverSide`，自動判 3:0 | Admin |
| 球隊整隊退賽 | Division 設 `withdrawalPolicy`，重算全組 | Admin |
| 賽程延後 | 改 `kickoffAt`，公開端顯示「延後至 HH:mm」徽章 | Admin |
| 場地更換 | 改 `venueId`，推送給該場地的訂閱者 | 賽務／Admin |
| 兩隊同分無法判定 | `hasUnresolvedTie=true`，積分榜該群顯示「待裁定」，Admin 手動拖曳排序並填理由 | Admin |
| 天候中斷 | `status='postponed'` + `note`；已進行比分保留於 timeline | Admin |
| PK 大戰 | `penaltyScore` 記錄，`result.method='penalty'`；積分榜視為平手（如規程另定則走設定） | 裁判 |
| 資格不符球員上場 | Admin 可事後改判 `walkover`，並記錄申訴案由 | Admin |

### 11.1 M2 補上的案例（審查後追加）

程式碼審查在第一版實作中找出 12 個缺陷，其中 5 個會直接影響現場。
以下案例是為了「以後不會再犯同樣的錯」而追加的，每一條都經過變異測試確認有鑑別力。

| # | 案例 | 為什麼要有 |
|---|---|---|
| T17 | 行為分跨場不可合併 | 同一球員「第一場黃 ＋ 第二場兩黃換紅」是 −4 不是 −3；算錯會改名次，還會憑空產生「待裁定」 |
| T18 | `clockSec` 優先於 `seq`；兩者皆缺時用陣列順序 | 事後補登的牌會讓 seq 錯亂，把 −5 誤判成 −4 |
| T19 | 比分不是數字時整場不計 | `Number(null)` 是 0，會把「沒填比分」判成 0:0 平手。`firestore.rules` 的 `validScore` 只掛在賽務分支，Admin 改分不經過它 |
| T20 | 解算結果套回去後可以再解算一次 | 解算會把場次設成 `ready`；若 `ready` 不算可寫入狀態，Function 重放會全數失敗，且分組賽改判後無法重解晉級 |
| T21 | 人工裁定要撐過重算 | 否則每次重算就跳回「待裁定」，晉級解算被永久卡住 |
| T22 | `canResolve` 缺資料時必須拒絕 | 少帶 `stageMatches`、stageId 拼錯都不可視為「全部打完」 |
| T23 | `awardPoints` / `penaltyPoints` 設定真的生效 | 宣告了設定卻沒接線，比沒有設定更危險 |
| T24 | `keepAsWalkover` 的未賽場次判 3:0 | 這是這個選項唯一的實質定義 |
| T25 | `mercyRule.cap ≤ 0` 要拉回 1 | cap 是後台可改的值，打成 0 會讓勝場變平手 |
| T26 | 烏龍球的兩種寫法都要擋 | schema 允許 `type:'own_goal'` 與 `goalType:'own'` |
| T27 | 沒被計入的場次與來源不明的牌不影響行為分 | 作廢場次的紅牌不該左右名次 |
