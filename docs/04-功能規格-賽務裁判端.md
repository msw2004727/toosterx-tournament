# 04｜功能規格：賽務／裁判端

> 對象：現場賽務、裁判、記錄台。全部以**手機單手操作**為前提。
> 鐵律：高頻操作 ≤ 3 步；每一次送出都必須有明確的「成功／待重送／失敗」回饋。

---

## 1. 角色與權限

| 角色 | code | 能做什麼 |
|---|---|---|
| 記錄員／賽務 | `scorer` | 檢錄、確認出場名單、開賽、輸入比分與事件、完賽送出 |
| 裁判 | `referee` | 同 `scorer`，另可簽核比賽結果 |
| 挑戰攤位 | `booth` | 只能操作被指派的 Challenge 關卡 |
| 管理員 | `admin` | 見 `05-功能規格-管理後台與報名.md` |

指派存放於根層 `staff/{uid}`：

```js
{
  uid: 'U...',
  name: '陳賽務',
  lineUserId: 'U...',
  roles: ['scorer'],
  assignment: {
    eventId: 'feda-cup-2026',
    date: '2026-10-11',
    venueIds: ['venue-a'],          // 指派場地
    divisionIds: ['adult-open'],    // 指派組別（可空 = 不限）
    challengeIds: []                // booth 角色用
  },
  deviceLabel: 'STF-03',
  active: true,
  createdAt, updatedAt
}
```

> 指派的意義：登入後**直接落到自己負責的場地**，不必再選。企劃書第二十二章說的「工作人員手機最好可以先指定為 Game 03」就是這個機制。

## 2. 登入流程

```
掃工作人員 QR（或點 LINE 群組連結）
      ↓
開啟 LIFF → LINE 授權
      ↓
liff.getIDToken() → callable: lineLogin
      ↓
Cloud Function 驗證 idToken，查 staff/{uid}
      ↓
回傳 Firebase Custom Token（含 role claim）
      ↓
signInWithCustomToken() → 進入賽務首頁
```

- 未在 `staff` 名冊中的人登入 → 顯示「你尚未被指派為工作人員」並提供聯絡窗口
- 登入狀態保存於 IndexedDB（Firebase 預設），關 App 再開不需重登
- 提供「切換身分」給同時擔任多職的人

## 4. QR 檢錄報到

### 4.1 為什麼要檢錄

基層賽事最常見的爭議是「冒名頂替」與「超齡球員」。檢錄的目的：

1. 確認上場球員 = 報名名單上的人
2. 確認年齡符合組別（U6/U8/U10）
3. 產生該場次的**出場名單（Match Sheet）**，成為事後申訴的依據

### 4.2 球員證 QR 設計

**Payload 格式**（純文字，不含個資）：

```
FEDA1.{eventShort}.{teamId}.{memberId}.{issuedAt}.{sig}

範例：FEDA1.FC26.t-101.m-101-07.1760227200.9f3c1a8e
```

| 欄位 | 說明 |
|---|---|
| `FEDA1` | 格式版本前綴，未來改版可辨識 |
| `eventShort` | 活動短碼，防止跨活動誤用 |
| `teamId` / `memberId` | 定位球員 |
| `issuedAt` | 發證 Unix 秒 |
| `sig` | HMAC-SHA256(payload, SECRET) 取前 8 碼十六進位 |

- 密鑰 `SECRET` 只存在 Cloud Functions 環境變數（Secret Manager），**絕不下放前端**
- QR 為**靜態**（不輪替），球員可截圖保存、可列印
- 撤銷機制：`member.qrRevoked = true`，離線名單同步時帶下

### 4.3 離線優先的驗證設計 ⭐

現場球場網路不穩是常態。設計採**預載名單 + 本機驗證**：

```
【賽前準備】（有網路時，賽務端自動執行）
下載當日「我的場地」所有場次的名單快照
  → 存入 IndexedDB：rosterCache[matchId][memberId] = {
        name, jerseyNo, photoThumb(base64 32×32), sig, revoked, eligibility
     }
  → 快取有效期 24 小時，每 10 分鐘背景更新

【現場掃碼】
掃到 QR → 解析 payload
  → 比對 eventShort 是否本活動         ✗ → 「非本賽事證件」
  → 比對 memberId 是否在本場次名單內    ✗ → 「不在本場出場名單」
  → 比對 sig 是否等於快取中的 sig       ✗ → 「證件無效或已重發」
  → 檢查 revoked                       ✗ → 「證件已作廢」
  → 檢查是否已檢錄（本機 + 遠端）        ✗ → 「重複檢錄」（顯示先前時間）
  → ✅ 通過：本機記錄，UI 立即回饋
  → 寫入 Firestore（離線則排隊）
```

**關鍵**：`sig` 的比對不需要密鑰——賽務端只比對「掃到的 sig」是否等於「名單快取裡的 sig」。密鑰只在 Function 產證時用到。這讓離線驗證成立，同時偽造者無法自行生成有效 sig。

**互動細節**

- 掃到即回饋，**不需按確認**（減少一步）
- 成功：綠底 + `vibrate(80)` + 短音；失敗：紅底 + `vibrate([60,60,60])` + 錯誤原因大字
- 連續掃描模式：0.8 秒防重複（同一 QR 在 3 秒內不重複觸發）
- 手動輸入：輸入背號 → 顯示該員照片與姓名 → 按「確認報到」（`method:'manual'`，會在稽核中標記）
- 顯示球員照片縮圖，讓賽務可目視比對

### 4.5 技術實作

```js
// 優先使用原生 BarcodeDetector（Android Chrome 支援）
if ('BarcodeDetector' in window) {
  const detector = new BarcodeDetector({ formats: ['qr_code'] });
  // requestVideoFrameCallback 迴圈偵測
} else {
  // fallback: jsQR（純 JS，iOS Safari 用）
}
```

- 相機權限：`getUserMedia({ video: { facingMode: 'environment' } })`
- 權限被拒時，退回手動輸入模式並顯示引導
- iOS Safari 需 HTTPS（Cloudflare Pages 預設有）

### 4.6 完成檢錄 → 產生出場名單

按「完成檢錄」後：

```
1. 檢查已檢錄人數 ≥ requiredMin（5人制 5 人 / 9人制 7 人，可設定）
   不足 → 警示，但允許 Admin 強制通過（記錄原因）
2. 產生 matchSheets/{matchId}__{teamId}
   - 已檢錄者進入 starters + substitutes
   - 賽務可拖曳調整先發／替補（或先發自動取前 N 位背號）
3. status = 'confirmed'，寫入 confirmedBy / confirmedAt
4. 雙方都 confirmed → match.status: checkin → ready
```

### 4.7 檢錄異常處理

| 情況 | 處理 |
|---|---|
| 球員忘記帶手機 | 手動輸入背號報到（留 `method:'manual'`） |
| QR 掃不出來（螢幕反光／破損） | 手動輸入 |
| 掃到別隊球員 | 顯示「此球員屬於 XX 隊」，不記錄 |
| 臨時加入球員（未報名） | 賽務不可自行新增；需 Admin 在後台加入名單並重發 QR |
| 網路全斷 | 全程離線模式，恢復後自動補傳；UI 明示「離線模式（已記錄 12 筆待同步）」 |
| 重複掃描 | 提示「已於 09:12 報到」，不重複寫入（doc id 天然唯一） |

路由：`#/staff/match/:matchId`

### 5.1 版面

```
┌────────────────────────────────────┐
│ ← 第31場 · A場        🟢 已連線     │
├────────────────────────────────────┤
│      臺中野狼   2 - 1   臺中猛虎     │  ← 大比分（可直接 +/-，見 5.3）
│           下半場  63:24              │  ← 計時器（大字等寬）
│  ┌──────────┐  ┌──────────────┐   │
│  │ ⏸ 暫停    │  │ ⏹ 結束下半場  │   │
│  └──────────┘  └──────────────┘   │
├────────────────────────────────────┤
│  ┌──────────┬──────────┬────────┐ │
│  │  ⚽ 進球  │  🟨 出牌  │ ⇄ 換人 │ │  ← 三個主要動作
│  └──────────┴──────────┴────────┘ │
├────────────────────────────────────┤
│  事件（可長按修正）                   │
│  63' ⚽ #7 王小明  野狼   [⋯]        │
│  58' 🟨 #4 林阿明  猛虎   [⋯]        │
├────────────────────────────────────┤
│  [ ✅ 完賽送出 ]                     │
└────────────────────────────────────┘
```

### 5.2 計時器

- 由裁判端控制 `clock.running` / `periodStartedAt` / `elapsedSecAtPause`
- **狀態變更才寫入 Firestore**（開始／暫停／結束期別），不是每秒寫
- 期別流程：`pre → h1 → ht → h2 → ft`（延長：`et1 → et2 → pk`）
- 補時：裁判可設定 `addedTimeSec`，公開端顯示 `45+3'`
- 計時器在賽務端本機跑（`requestAnimationFrame`），斷網不影響

### 5.3 記錄進球（3 步）

```
① 點「⚽ 進球」
      ↓
② 選擇隊伍（左右兩大按鈕，各佔半個螢幕寬）
      ↓
③ 選擇進球球員（該隊出場名單九宮格，大按鈕含背號＋姓名）
      ↓
   ✅ 比分 +1、事件寫入、震動回饋
```

**可選的第 4 步（不阻擋）**：選助攻者／進球方式。畫面顯示「已記錄 ⚽ #7 王小明 [ 補充助攻 ]」，5 秒後自動消失。

**快速模式**：若當下無法確認進球者（常見於兒童組），可按「不指定球員」直接記分。事後可在事件列表補上。

### 5.4 記錄卡片

```
① 點「🟨 出牌」→ ② 選隊伍 → ③ 選球員 → ④ 選 黃 / 兩黃換紅 / 直接紅
```

- 系統自動偵測：同一球員第二張黃牌 → 提示「此為第二張黃牌，是否記為兩黃換紅？」
- 紅牌後該球員自動從出場名單移出（`matchSheet` 標記 `sentOff`）

### 5.5 換人

```
① 點「⇄ 換人」→ ② 選隊伍 → ③ 選下場球員 → ④ 選上場球員
```

- 顯示該隊已用換人次數 / 上限（可設定，如 5 人制不限、9 人制 7 人次）
- 超過上限時警示但不阻擋（現場規則可能彈性）

### 5.6 完賽送出

```
點「✅ 完賽送出」
      ↓
確認畫面：
  ┌──────────────────────────┐
  │  臺中野狼  2 - 1  臺中猛虎 │
  │  半場 1-0                 │
  │  事件 6 筆                │
  │  ⚠️ 事件加總(2:1) 與比分一致 │
  │  [ 取消 ]   [ 確認完賽 ]   │
  └──────────────────────────┘
      ↓
寫入 status='finished', lock.locked=true
      ↓
成功畫面（大綠勾）＋「已送出，積分榜更新中…」
      ↓
3 秒後自動回到賽務首頁，並顯示下一場
```

**一致性檢查**：若 timeline 事件加總 ≠ 比分，確認畫面顯示橘色警示「事件加總為 2:0，與比分 2:1 不同，仍要送出嗎？」——**警示但允許送出**（以裁判判定為準）。差異會記錄在 `match.scoreMismatch = true`，供 Admin 事後檢視。

### 5.7 送出狀態三態

這是企劃書第三十二章的核心要求。實作方式：

```js
// 不使用 Firestore 的 await（離線時會 pending 不 resolve）
const localWrite = setDoc(ref, data);          // 不 await，本機立即生效
setPending(true);
localWrite
  .then(()  => setStatus('saved'))             // 伺服器確認
  .catch(e => setStatus('failed', e));
// 同時監聽 snapshot.metadata.hasPendingWrites
onSnapshot(ref, { includeMetadataChanges:true }, s => {
  setStatus(s.metadata.hasPendingWrites ? 'queued' : 'saved');
});
```

UI：

| 狀態 | 顯示 |
|---|---|
| `queued` | 🟡「已記錄，等待同步」按鈕維持可用 |
| `saved` | 🟢「已儲存」 |
| `failed` | 🔴「儲存失敗：權限不足／資料錯誤」＋ [重試] [複製內容] |

**絕不允許**：按下送出後 UI 顯示成功但實際沒寫入。

## 6. 管理員 LIVE 介面

路由：`#/admin/match/:matchId`。在賽務台的基礎上追加：

| 功能 | 說明 |
|---|---|
| **直接改比分** | 點比分數字可直接輸入任意值，必填 `reason` |
| **編輯／作廢事件** | 任一事件可改分鐘、球員、類型，或標記 `voided`（不真的刪除） |
| **退回完賽** | `finished` → `live`，解除 `lock`，必填原因 |
| **改判棄賽** | 一鍵設 `walkover`，選擇棄賽方，自動判 3:0 |
| **延期／取消** | 設 `postponed` / `cancelled`，可改 `kickoffAt` |
| **更換隊伍** | 排名階段的隊伍可手動指定（覆寫晉級解算） |
| **切換直播來源** | 改 `stream.videoId` 或關閉直播 |
| **強制重算積分榜** | 呼叫 `recalcStanding`（callable） |
| **稽核紀錄** | 該場次所有修改的時間軸 |

所有動作皆寫入 `audits`，並在公開端該場次顯示小字「已於 HH:mm 更正」。

## 9. 現場備援方案（Plan B）

網路全斷且超過 30 分鐘時：

1. 賽務端提供「**列印今日賽程與空白記分表**」（Admin 端匯出 PDF，賽前印出備份）
2. 紙本記錄後，恢復連線由 Admin 補登（後台有「補登比分」批次介面）
3. 補登的場次標記 `source:'paper-backfill'`，不影響稽核完整性

> 賽前必做：把三日賽程與空白記分表各印 2 份放在賽務桌。系統再好，紙本備援是基層賽事的基本禮貌。
