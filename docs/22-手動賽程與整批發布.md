# 手動賽程與整批發布

主辦 2026-10-04 決定由專責 UI 設計 AI 顧問協作，採「沿用既有賽制、逐場手動安排」及「私有草稿 → 衝突檢查／差異預覽 → 整批發布」。

## 主辦操作

1. 管理員或總管進入「賽程管理」，選組別，再選「手動安排」。
2. 已有場次沿用現有分組與 ID。沒有場次時，使用核准隊伍及匹配的賽制範本建立裝置草稿；需要調整分組可先使用既有分組操作，未建立場次的分組順序會帶入新草稿。
3. 循環賽把球隊卡片拖入主／客隊位置；卡片可重複使用，顯示已安排／應有場數。手機及鍵盤可點選球隊，再指定位置。替換已有球隊須確認，發布前可撤銷。
4. 時間採 24 小時制下拉，每 5 分鐘一格；既有不整除 5 分鐘的時間保留。日期、比賽長度及場地依組別與 `config/schedule`，不改競賽規章。
5. 淘汰賽顯示排名或勝敗隊來源，手動安排時間與場地；隊伍仍由既有晉級管線解算。
6. 檢查完整對戰及全賽事場地／隊伍撞場。錯誤阻止發布，休息不足／等待過久只提醒。確認前後差異並填安排原因後，一次發布完整組別。

草稿只存本裝置，依使用者、活動、組別及排程版本隔離；拖曳與改選單均不寫公開 `matches`。舊草稿不會自動覆蓋新版。發布須連線；若回應遺失，保留原請求與代碼，可重送取得同一份收據。

## 保護與資料

- 已開打、曾有比分／結果、非賽前期別、鎖定或曾改判的場次不可更動；組別有任何已打過場次時，整組對戰隊伍鎖定，未開打場次仍可改時間與場地。
- 編輯既有賽程保留 ID、編號、比分、晉級內容及無關子集合；換對戰前必須尚未開打且沒有事件紀錄。被更換對戰的舊出場名單與檢錄失效，原資料封存在稽核。
- 新建使用新的世代 ID。已有編號保持穩定，新場次按開賽時間接續編號。
- 每一對必要循環賽對手必須完整且只出現範本要求次數；不可自賽、跨小組、加入未核准／退賽隊伍或篡改晉級位置。
- 新 callable `publishManualSchedule` 在 Firestore 交易中重讀角色、版本、來源、核准名單、賽制、排名規則、場地及全賽事場次。賽程、發布狀態、收據、before／after／操作者／原因稽核一起提交；超過容量先拒絕，不分批發布。
- `manageEvent` 的 `schedule.move` 原本僅由 UI 鎖住已開打場次，後端漏查；本次補上與 `shift`／`place` 相同的權威護欄，並以直接呼叫與反向變異驗證。

## 驗收

引擎單元、Firestore Emulator 交易與 Playwright 測試涵蓋配對完整性、晉級來源、跨組衝突、已開打鎖定、資料變更、併發、稽核失敗回滾、原請求重送，以及桌機拖曳、真實觸控拖曳／正常捲頁、點選／鍵盤、320px 深淺色與長隊名。完整測試數與部署來源以本次 release ledger／CI 為準。
