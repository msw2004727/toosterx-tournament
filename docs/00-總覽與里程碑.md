## 1. 專案定位

### 1.1 兩層目標

| 層次 | 目標 |
|---|---|
| **活動層** | 讓 FEDA CUP 2026 三日賽事的賽程、比分、排名、檢錄、直播全部數位化，現場賽務不再依賴 Excel 與白板 |
| **產品層** | 驗證 ToosterX 的 Tournament Engine 與 Challenge Engine 是否具備「可設定、不寫死」的通用性，作為後續盃賽／聯賽／企業運動會的產品基礎 |

### 1.2 一句話定義

> 一個以手機為主、公開頁免登入、賽務端兩三步完成操作的**賽事即時營運網站**；賽制與遊戲規則以設定檔驅動，而非寫死在程式碼。

### 1.3 明確的非目標（本階段不做）

- 不做完整電商金流／電子園遊券（僅預留 `attemptSource` 欄位）
- 不做影音自製串流（直播一律外掛 YouTube）
- 不做球員生涯累積數據跨賽季系統（本次僅單一 Event 內統計）
- 不做華麗抽獎動畫（僅記錄資格、計算張數、匯出名單）
- 不做多語系（先做繁體中文，但字串集中管理以利後續擴充）

## 4. 技術決策（已定案）

依 ToosterX 現有專案（`msw2004727/FC`）的技術棧與治理規則，本站採**同平台、獨立專案**部署。

| 面向 | 決策 | 理由 |
|---|---|---|
| **前端** | Vanilla ES6 + HTML + CSS，無打包工具 | 與 FC 一致，維護心智負擔最低；靜態站 CDN 快取效果好 |
| **資料庫** | Firebase Firestore（新專案 `feda-cup-2026`） | 與 FC 一致；`onSnapshot` 天生適合即時比分 |
| **讀取** | 前端直連 Firestore（即時監聽） | 免自建 WebSocket，即時比分零延遲 |
| **寫入** | `firestore.rules` 守衛 + Cloud Functions v2 處理運算 | 與 FC 一致的純 Firebase 路線 |
| **後端運算** | Cloud Functions v2（Node.js 22），region `asia-east1` | 積分／排名／晉級／QR 簽章／匯出 |
| **認證** | 公開頁免登入；工作人員 LINE LIFF + Firebase Auth（Custom Token） | 觀眾零摩擦；工作人員可稽核 |
| **權限** | `rolePermissions/{role}` + `userPermissionGrants/{uid}` 雙層 | 沿用 FC 的動態權限機制，免刷新 token |
| **靜態託管** | Cloudflare Pages（新專案）＋ 自訂網域 | 與 FC 同平台，main branch push 自動部署 |
| **離線** | Service Worker（僅快取 App Shell 與靜態資源，HTML 不 cache-first） | 遵守 FC 的 R-REL-013 |
| **測試** | Jest（單元／rules）＋ Playwright（E2E） | 與 FC 同一套工具鏈 |
| **版本** | `0.YYYYMMDD{suffix}`，由 `scripts/bump-version.js` 統一遞增 | 遵守 FC 的 R-REL-003 |

### 4.1 為什麼寫入不走 Python FastAPI

你平常的預設後端是 Python（Flask／FastAPI on Cloud Run），但這個站選純 Firebase，原因有三：

1. **即時比分是核心**。Firestore `onSnapshot` 讓比分變更在 200ms 內推到所有觀眾裝置。若寫入走 FastAPI，仍要靠 Firestore 推播，等於多一層卻沒有換到好處。
2. **現場網路不穩**。Firebase SDK 內建離線佇列，賽務人員在球場收訊不好時送出的比分會自動排隊重送——這正是企劃書第三十二章「不能出現以為送出但其實沒送出」的解法。自建 API 要自己做這一層。
3. **與 FC 同一套維運**。同一個 Firebase 控制台、同一套 rules 測試、同一套部署 lane，不必再養一個 Cloud Run 服務。

> 若未來要接 ToosterX 主站的 Python 服務（例如報表、金流），以 Cloud Functions 對外發 webhook 即可，架構不需重做。

### 4.2 環境規劃

| 環境 | Firebase 專案 | 網域 | 用途 |
|---|---|---|---|
| `dev` | `feda-cup-dev` | `dev.fedacup.pages.dev` | 開發與 Emulator |
| `staging` | `feda-cup-stg` | `stg.fedacup.pages.dev` | 賽前彩排、壓測、假資料全流程 |
| `prod` | `feda-cup-2026` | `cup.toosterx.com`（建議） | 正式活動 |

## 5. 產品原則（開發時的判斷依據）

| 原則 | 具體標準 |
|---|---|
| **Mobile First** | 所有賽務介面以 390×844（iPhone 14）為基準設計；桌機是加分項 |
| **Fast Operation** | 高頻操作 ≤ 3 步：選場次 → 輸入比分 → 確認。單手可完成 |
| **Configurable** | 賽制、積分、同分排序、遊戲成績型態一律走設定檔，程式不得出現 `if (組別 === '女子組')` |
| **Offline Tolerant** | 送出結果必須明示「已儲存／待重送／失敗」三態，絕不沉默失敗 |
| **Auditable** | 所有結果性資料的修改都留下 原值／新值／修改者／時間／原因 |
| **MVP First** | 順序：能用 → 好用 → 自動化 → 漂亮 |

## 7. 第一階段完成定義（Done Definition）

### 7.1 Tournament Done

系統能在**不使用 Excel 重算**的前提下完成：

```
建立 38 隊 → 建立 6 組別 → 自動產生賽程
  → 現場輸入比分 → 自動積分 → 自動排名
  → 自動產生下一階段對戰 → 完成各組 1–8 名最終排名
```

### 7.2 Check-in Done

一位球員能：

```
報名時登記 → 收到球員證 QR → 賽前檢錄出示
  → 賽務掃碼 → 系統驗證身分與參賽資格（含離線）
  → 出場名單鎖定 → 該場次可上場
```

### 7.3 LIVE Done

一場比賽能：

```
裁判端開賽 → 記錄進球／卡／換人 → 公開端 1 秒內同步
  → YouTube 直播並列顯示 → 完賽簽核 → 積分榜即時更新
```

### 7.4 Challenge Done

一位沒有 ToosterX 帳號的路人能：

```
掃活動 QR → 建立 Game Pass → 取得玩家 QR
  → 攤位掃碼 → 輸入成績 → 排行榜出現名次 → 取得抽獎資格
```

## 9. 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 球場網路不穩／無 4G | 賽務無法送出比分 | Firebase 離線佇列＋明確三態提示；檢錄預載離線名單；備援手機熱點 |
| 兒童組賽制當天臨時調整 | 賽程需重建 | Admin 可手動新增／刪除／改對戰隊伍，並可鎖定不觸發自動晉級 |
| 球隊棄賽 | 積分計算錯亂 | 內建 `walkover` 處理：預設判 3:0（可設定），並記錄棄賽原因 |
| 同分無法判定 | 名次卡住 | 同分排序規則走設定檔，最後一層一律落到「主辦裁定」由 Admin 手動指定名次 |
| 掃碼硬體不足 | 檢錄塞車 | 純網頁掃碼（`BarcodeDetector` + `getUserMedia` fallback `jsQR`），任何手機皆可；另備手動輸入球員編號 |
| YouTube 直播中斷 | 公開頁破圖 | 直播區塊可由 Admin 一鍵切換為「暫停直播」佔位圖 |
| 工作人員誤操作 | 資料錯亂 | 完賽後鎖定；解鎖需 Admin 權限；所有修改留稽核 |
| 個資外洩 | 法遵風險 | 身分證字號一律不存全碼（僅後四碼且僅 Admin 可讀）；未成年球員照片需監護人同意欄位 |
