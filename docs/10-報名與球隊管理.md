## 0. 這份規格解決什麼問題

沒有球隊資料，賽程、積分榜、公開端全都是空的。
相依鏈是這樣的，報名在最上游：

```
報名 → 球隊與名單 → 產生賽程 → 賽務端記分 → 公開端顯示
```

所以報名系統的優先序高於公開端。

## 1. 身分模型（重大變更）

### 1.1 全站角色

| 角色 | code | 能做什麼 | 誰能指派 |
|---|---|---|---|
| 大總管 | `super_admin` | **唯一能改別人身分的人**。指派／撤銷所有角色 | 種子資料（第一位）／既有大總管 |
| 管理員 | `admin` | 賽務全權、改判、退回完賽、審核報名、匯入名單 | 大總管 |
| 記錄員／賽務 | `scorer` | 檢錄、記分、完賽送出 | 大總管、管理員 |
| 裁判 | `referee` | 同賽務 | 大總管、管理員 |
| 挑戰攤位 | `booth` | 指派關卡的成績登錄 | 大總管、管理員 |

> **`venue_lead`（場地主任）已移除。** 覆核完賽（`finished → confirmed`）改由 Admin 執行。
> 移除理由：主辦當天在現場即可覆核，多一層角色只增加設定與教學成本。
> 代償措施見 §5.3「三分鐘撤回」。

**權限升級只有一條路**：只有 `super_admin` 寫得動 `staff/{uid}.roles`。
Admin 再怎麼樣也升不了自己，也造不出第二個大總管。這條線由 rules 強制執行，
**不依賴動態權限表**——FC 的 R-IAM-004 就是動態權限與 rules 不同步造成的已知漏洞，
我們不複製那個模式。

### 1.2 隊長不是全站角色

隊長是**球隊文件上的一個欄位**（`teams/{teamId}.captainUid`），不是 `staff` 裡的角色。

理由：同一個人可能是 A 隊隊長、同時是 B 隊球員。做成全站角色就分不清了。
（FC 的 `isCurrentUserTeamCaptainOrLeader(teamId)` 也是這個做法。）

### 1.3 監護人與球員是兩層

**一個 LINE 帳號可以對應多個球員。**

```
LINE 帳號（guardianUid）
   ├── 球員 A：U8 龍井白鯊 · #7
   └── 球員 B：U10 大甲金剛 · #4
```

- 兒童組（U6／U8／U10）：家長用自己的 LINE 登入，代小孩報名
- 成人組（女子／興趣／公開）：本人登入，`guardianUid === 自己`，介面上不出現「監護人」字樣
- **球員證 QR 綁在球員（memberId）身上，不是帳號**
- 家長端看到的是「我的球員（N）」，每位都能叫出自己的球員證

同意書因此天然解決：家長本人送出即為同意，存下 `{ given, at, byUid }` 當證據。

**家長沒有 LINE 的回退**：不在隊長端開第二條路（兩條路的資料品質會不一致），
改由主辦後台代為建立，標記 `source: 'manual'`，稽核看得出來。

### 1.4 大總管怎麼找到人：`users/{uid}`

LINE 的 userId 沒辦法憑空查，所以任何人登入時都要留下一筆自己的紀錄，
大總管才有名單可以指派。

```js
users/{uid} {
  uid, displayName, pictureUrl,
  firstSeenAt, lastSeenAt,
  // 快取，方便後台列表；權威仍是 staff/{uid}.roles
  roles: ['scorer'] | []
}
```

**第一位大總管的產生**：demo 由種子資料寫入；正式站由主辦本人先 LINE 登入一次，
再於 Firebase Console 手動建立 `staff/{uid}`。之後所有身分都由他指派。

## 2. 資料模型

### 2.1 `events/{eventId}/teams/{teamId}`

```js
{
  teamId, eventId, divisionId,
  name,              // 正式隊名
  shortName,         // 顯示用短名（賽程表、比分板）
  abbr,              // 三字母縮寫，選填
  colorPrimary,      // 隊伍代表色，選填；未填則用組別色

  captainUid,        // 隊長（LINE uid）
  captainName,
  contact: { phone, email, lineDisplayName },

  status,            // draft | submitted | approved | rejected | withdrawn
  submittedAt, reviewedAt, reviewedBy, rejectReason,

  inviteCode,        // 6 碼英數，給 QR 與邀請連結用
  announcement: { text, updatedAt, updatedBy },   // 單則，最新的

  rosterLocked,      // 審核通過後為 true
  memberCount,       // 已核准人數（由 Function 維護）

  seed,              // 種子序，主辦排定
  finalRank,         // 賽後最終名次
  createdAt, updatedAt
}
```

**隊徽不收圖**（見 §6）。顯示時用隊名首字圓標，配該組別的顏色。

### 2.2 `events/{eventId}/teams/{teamId}/members/{memberId}`

```js
{
  memberId,
  guardianUid,       // 誰報的（家長或本人）
  isSelf,            // true = 成人自己報名

  name, birthDate, idLast4,
  jerseyNo, position,
  kind,              // player | coach | staff

  status,            // pending | approved | rejected | removed
  appliedAt, decidedAt, decidedBy,

  note,              // 隊長備註，純文字，只有隊長與主辦看得到
  consent: { given, at, byUid },
  source,            // self | guardian | manual（主辦代建）

  createdAt, updatedAt
}
```

**加入申請不另開集合**，就是名單上 `status === 'pending'` 的那幾筆。
隊長在同一份名單上按同意，資料不用搬移，也不會出現「申請通過但名單沒同步」。

公開投影（`teams/{teamId}/roster/{memberId}`）由 Function 從 `status === 'approved'`
的成員產生，未滿 13 歲顯示遮蔽名（R-PRIV-001）。

### 2.3 `config/registration`

```js
{
  open: true,              // 主辦手動開關
  opensAt, closesAt,       // 截止日；到期自動關閉
  maxTeamsPerAccount: 3,   // 防洗版
  // 人數上下限：不設限，由主辦審核時判斷
  minMembers: null,
  maxMembers: null
}
```

**開放條件** = `open === true` **且** 現在時間在 `opensAt` 與 `closesAt` 之間。
兩個條件是 AND，所以主辦隨時能提前關閉，也能延長。

## 3. 報名流程

```
公開報名頁（免登入可看，要送出才需登入）
      ↓ LINE 登入
建立球隊（status: draft）→ 系統產生 inviteCode
      ↓
隊長把 QR／連結給隊友
      ↓
隊友（或家長）掃碼 → LINE 登入 → 填球員資料 → 送出（status: pending）
      ↓
隊長逐筆同意／婉拒（→ approved / rejected）
      ↓
隊長按「送出報名」【名單凍結，隊長不能再改】
      ↓
主辦審核 ──通過→ approved【名單正式鎖定，要改找 Admin】
        └─退回→ 解凍回 draft，隊長改完再送
```

### 3.1 為什麼送出當下就凍結

從隊長送出到主辦審核可能隔好幾天。若這期間名單還能改，
主辦審的跟通過的會是兩份不同的東西。所以送出即快照；
隊長想改就按「撤回報名」退回 draft。

### 3.2 名單鎖定 ≠ 不能調度

這兩件事常被混淆，明確區分：

| | 鎖定後 |
|---|---|
| **球隊名單**（誰在這支隊） | 鎖住，要改找 Admin |
| **出場名單**（這場誰先發、誰替補） | **每場都能改**，賽務自己就能調 |

有人受傷、有人沒到，賽務在賽務台調先發替補即可，
不需要動球隊名單，也不需要找主辦。

### 3.3 邀請碼的安全模型

`inviteCode` 放在公開可讀的 team 文件上，任何人都拿得到。**這是刻意的。**

理由：知道碼只能「申請」，不等於「加入」——**隊長同意才是閘門**。
配套：同一個帳號對同一隊只能有一筆申請（doc id = `${teamId}__${guardianUid}__${seq}`
不足以防，改由 rules 檢查已存在的 pending），一個帳號最多建 3 支隊。

## 4. 隊長能做什麼

| 動作 | 限制 |
|---|---|
| 同意／婉拒加入申請 | 名單凍結前 |
| 移除已核准的隊員 | 名單凍結前；移除是 `status: 'removed'`，不刪文件 |
| 編輯隊員備註 | 隨時（凍結後也可以，備註不影響參賽資格） |
| 發布球隊公告 | 隨時。單則、純文字、只有隊員與主辦看得到 |
| 編輯隊伍資料 | 名單凍結前 |
| 送出／撤回報名 | 審核通過前 |
| 轉移隊長身分 | 給隊上任一位已核准成員，寫稽核 |

**球隊公告不做 LINE 推播。** 要推播得另外申請 Messaging API，
而且很容易變成騷擾來源。隊員進球隊頁就看得到。

## 5. 權限邊界（firestore.rules 要落實的）

### 5.1 身分授權

```
只有 super_admin 能寫 staff/{uid}.roles
admin 不能改任何人的身分（包含自己）
角色白名單不含 super_admin —— 大總管不能由介面產生第二個
```

### 5.2 球隊與名單

```
teams              公開可讀
                   建立：登入 + 報名開放中 + 未超過每帳號 3 隊上限
                   更新：captainUid == uid（且未鎖定）或 isAdmin()
                   status 只能沿 draft → submitted → approved/rejected 走
                   rosterLocked 只有 Admin 能改

members            讀：隊長、該筆的 guardianUid、賽務以上
                   建立：登入 + 報名開放中 + 該隊未凍結 + status 必須是 pending
                   更新：隊長（決定 status、備註）或 Admin
                   刪除：一律禁止（移除是改 status）
```

### 5.3 三分鐘撤回（取代場地主任）

拿掉場地主任後，所有完賽修正都要找 Admin。現場最常見的是：

> 賽務按完送出，五秒後發現最後那顆球記成客隊了。

所以允許**賽務在送出後三分鐘內自行撤回一次**：

**實作（firestore.rules 分支 D，2026-08-29 完成）**：

```
isScorer() 且為指派場地
  且 resource.data.status == 'finished'                    ← 已 confirmed 就不行
  且 resource.data.scoreSubmittedBy == uid()               ← 只有送出的本人
  且 resource.data.scoreSubmittedAt != null
  且 request.time < scoreSubmittedAt + duration.value(3,'m')
  且 request.resource.data.status == 'live'
  且 request.resource.data.lock.locked == false
  且 request.resource.data.scoreSubmittedAt == null        ← 不准留著讓視窗續命
  且 只動 status / period / lock / result /
       scoreSubmittedAt / scoreSubmittedBy / updatedAt / updatedBy
```

比原本的草案多了三道：

| 加了什麼 | 擋掉什麼 |
|---|---|
| `scoreSubmittedBy == uid()` | 同場地的另一位賽務撤掉別人送出的成績 |
| 撤回時必須把 `scoreSubmittedAt` 清成 `null` | 保留舊時間戳讓三分鐘視窗一直續命 |
| `serverStampedSubmit()`：`scoreSubmittedAt` 只能是原值或 `request.time` | 完賽時先塞一個 2099 年的時間戳，之後永遠都在「三分鐘內」 |

比分**不在**可改欄位裡：撤回只是把場次退回進行中，比分與事件全部保留，
要改比分請在退回之後照常改（那條路徑本來就有稽核）。
退回的期別取「實際打過的最後一個 `period_start`」，不是一律當成下半場——
延長賽或 PK 之後撤回會退錯期別。

三分鐘夠發現手誤，短到不可能拿來竄改結果。超過就找 Admin，這條線不變。

**⚠️ 離線陷阱**：三分鐘以**伺服器時間**為準（否則改手機時間就能繞過）。
但離線送出的寫入要等恢復連線才真正送達，那時可能早就超過三分鐘。
這是正確的行為，但介面不能騙人——

> **離線時不顯示倒數計時**，也不顯示撤回按鈕，
> 改顯示「完賽還在待同步，連上線之後才會開始計算可撤回時間」。
> 真的同步成功了，才開始跑那三分鐘。

寧可少給一個功能，也不要給一個會失效的倒數。

實作上有兩種離線，兩種都要擋：

1. **離線送出**：`serverTimestamp()` 在本機快照裡是 `null`，
   所以「算不出剩幾秒」——這種很好擋
2. **線上送出之後才斷線**：時間戳是真的、三分鐘也還沒到，
   只有 `isOnline()` 這一道擋得住。**這才是危險的那一種**

第 2 種在測試上特別容易漏：只測第 1 種的話，把 `online` 檢查整條拿掉
測試仍然全綠（被第 1 種的 `null` 防線接住了）。
`tests/e2e/undo-finish.spec.js` 有一條專門測第 2 種（見 R-TEST-001）。

## 6. 不收圖片的取捨

報名階段**不收隊徽與球員照片**，因此不需要 Firebase Storage。

| | 影響 |
|---|---|
| 隊徽 | 用隊名首字圓標，配組別色 |
| 公開端球員頁 | 沒有大頭照，只有背號姓名位置 |
| **M5 檢錄** | 原本可「掃碼 → 跳出照片 → 目視比對」，**現在只能核對姓名／背號／生日**。防「拿別人的證」少了一道 |

**但 Blaze 仍然必要**：家長用 LINE 登入 → LIFF 拿 idToken →
必須有後端驗證換成 Firebase 身分（`lineLogin` callable）→ 那是 Cloud Functions。
沒有中間路線：未經後端驗證的 idToken，firestore.rules 認不得他是誰。

積分重算、晉級解算、球員證 QR 簽章也都要 Functions。

## 7. 設計系統：對齊 FC

### 7.1 為什麼要對齊

同一個人維護兩個專案，token 命名一致的話元件可以互相搬。
所以**中性色、文字階層、圓角、陰影、動效、命名全部照 FC**，
只在上面疊一層賽事專用的語意色。

### 7.2 主題切換

FC 用 `[data-theme="dark|light"]` 屬性，**不用 `prefers-color-scheme`**。
我們採同樣機制，但加一個 `system` 態：

```
第一次造訪 → 跟系統走
使用者手動切過 → 記在 localStorage，之後照他的選擇
```

三態：`system / light / dark`。

### 7.3 Token（照抄 FC 的部分）

```css
:root {
  --radius: 14px;  --radius-sm: 8px;  --radius-full: 999px;
  --shadow: 0 2px 12px rgba(0,0,0,.12);
  --shadow-lg: 0 8px 32px rgba(0,0,0,.18);
  --transition: .25s cubic-bezier(.4,0,.2,1);
  --topbar-h: 56px;  --bottombar-h: 64px;
}

[data-theme="light"] {
  --bg-root:#f4f6f9;  --bg-card:#ffffff;  --bg-elevated:#f0f2f5;  --bg-input:#f0f2f5;
  --border:#dfe3ea;
  --text-primary:#1a1d24;  --text-secondary:#5a6478;  --text-muted:#8892a4;
  --danger:#dc2626;  --warning:#d97706;  --info:#2563eb;  --success:#059669;
  --overlay:rgba(0,0,0,.35);
}

[data-theme="dark"] {
  --bg-root:#0d1017;  --bg-card:#181d27;  --bg-elevated:#222838;  --bg-input:#222838;
  --border:#323a4e;
  --text-primary:#f5f7fa;  --text-secondary:#e8ecf2;  --text-muted:#cdd3de;
  --danger:#f87171;  --warning:#fbbf24;  --info:#60a5fa;  --success:#34d399;
  --overlay:rgba(0,0,0,.65);

```

### 7.4 賽事識別色（我們自己的那一層）

FC 的 accent 是 emerald；FEDA CUP 換成**球場綠**，並保留賽事語意色：

```css
[data-theme="light"] {
  --accent:#0f7a52;  --accent-hover:#0c6544;  --accent-bg:rgba(15,122,82,.10);
  --live:#c2410c;    /* LIVE、進球 */
  --gold:#b45309;    /* 冠軍、獎項 */
}
[data-theme="dark"] {
  --accent:#3fbf8a;  --accent-hover:#6ee7b7;  --accent-bg:rgba(63,191,138,.16);
  --live:#fb923c;
  --gold:#fbbf24;
}

/* 六個組別色，兩個主題各一組（深色模式要提高明度才看得清） */
--div-u6  --div-u8  --div-10  --div-women  --div-fun  --div-open
```

### 7.5 圖示：不再用 emoji

FC 的規則是 **16–18px 線性 SVG，功能按鈕禁用 emoji**。我目前違規之處：

- 賽務台三顆主要動作（⚽🟨⇄）
- 連線狀態燈（●）
- 賽程清單的狀態圓點（✅🔴🔵⚪）
- 完賽送出（✅）、返回（←）

全部換成 SVG sprite。理由不只是好看：**emoji 在不同手機上字型不同、大小不一致**，
而且 Android 與 iOS 的 ⚽ 長得不一樣。

### 7.6 窄版優先

| 寬度 | 要求 |
|---|---|
| **360px** | 主要設計基準（多數 Android） |
| 320px | 不能破版（iPhone SE） |
| 390px | 常見 iPhone |
| ≥ 840px | 置中限寬，不做多欄（賽務端本來就是手機用） |

檢查標準：**任何頁面在 320px 都不能出現橫向捲動**。

## 8.5 與 FC-Football 的關係（2026-08-29 定案）

FC-Football 專案：`fc-football-6c8dc`（已是 Blaze，有真實使用者在用）。

### 不共用資料庫

| 風險 | 說明 |
|---|---|
| **rules 是專案級、整份覆蓋** | 我們部署 `firestore.rules` 會把 FC 的整份規則換掉。FC 是有真實使用者的正式系統，一次部署失誤就是全站掛掉或資料外洩 |
| **索引部署會刪除未列出的索引** | `firebase deploy --only firestore:indexes` 預設刪掉不在檔案裡的，可能刪掉 FC 正在用的 |
| **我們有 demo，FC 明文禁止 demo**（R-CTX-001） | 共用等於把 38 隊假球隊、1177 筆種子資料寫進 FC 正式庫 |
| **部署節奏綁死** | 改 FEDA CUP 的規則要重跑 FC 全部的 rules 測試 |

風險完全不對稱：FEDA CUP 是一次性活動，FC 是長期營運系統。**兩個專案維持獨立。**

### 但身分完全共用

已驗證：**FC 把 LINE userId 直接當成 Firebase Auth UID**
（`U7774e1410479bafff4997f51b2c47b95` 在 FC-Football 的 Authentication 中存在，
2026-02-25 建立）。

FEDA CUP 的 `lineLogin` Function 產生 custom token 時，**`uid` 必須直接用 LINE userId**，
與 FC 一致。這樣同一個人在兩個專案裡的 uid 完全相同，不需要共用資料庫就能對得起來：

- 使用者不必註冊兩次，兩邊都是 LINE 登入
- `teams/{id}.captainUid` 與 FC 的 `users/{uid}` 是同一個鍵
- 日後要把賽事成績寫回 FC 的個人統計，有共同主鍵

### ⚠️ 不可逆的前提：LIFF 必須建在同一個 LINE Provider 底下

LINE 官方文件明確規定：

> User IDs are issued **per provider, not per channel**.
> If the provider is the same, the user ID is the same regardless of the channel type.
> User IDs are issued different values for each provider, even for the same user.

所以 FEDA CUP 的 LIFF Channel **必須建在 FC-Football 所屬的同一個 Provider 底下**。
若另開 Provider，同一個人在兩邊會拿到**完全不同的 userId**，而且一旦球隊開始報名，
錯的 ID 就寫進資料裡了，回頭要重做。

**這是建 LIFF 之前唯一必須確認的事。**

### 之後若要真的讀 FC 的資料

不共用資料庫也能跨專案讀：在 FEDA CUP 的 Cloud Function 裡用 FC 的 service account
初始化第二個 Admin App，或反過來由 FC 開一個 callable 給 FEDA CUP 呼叫。
這是「需要時再加」的東西，不影響現在的架構。
