### 1.1 讀寫分工原則

| 動作 | 路徑 | 理由 |
|---|---|---|
| 讀取任何公開資料 | 前端直連 Firestore | 即時、低延遲、免 API 層 |
| 寫入比分 / 事件 | 前端直寫 Firestore（rules 守衛） | 利用 SDK 離線佇列，斷網自動重送 |
| 積分榜 / 晉級運算 | Cloud Function 觸發器 | 避免客戶端算錯；單一真相來源 |
| QR 簽章 / 驗簽 | Cloud Function（callable） | 密鑰不得下放前端 |
| 匯出、批次 | Cloud Function（callable） | 需 Admin SDK 權限 |

> **關鍵取捨**：比分「寫入」放在客戶端而非 callable，是為了拿到 Firestore 的離線佇列。代價是 rules 必須寫得很緊（見 `07-權限安全與CloudFunctions.md`）。

## 2. Firestore 資料模型

### 2.1 集合總覽

```
events/{eventId}                         活動（本次只有一筆：feda-cup-2026）
│
├── divisions/{divisionId}               組別
│   └── stages/{stageId}                 階段
│       └── groups/{groupId}             小組（僅循環賽階段有）
│
├── teams/{teamId}                       參賽隊伍
│   └── members/{memberId}               球員與職員
│
├── matches/{matchId}                    場次（扁平，跨組別）
│   └── timeline/{timelineId}            比賽事件（進球／卡／換人／期別）
│
├── standings/{standingId}               積分榜（id = `${divisionId}__${stageId}__${groupId}`）
│
├── venues/{venueId}                     場地
│
├── checkins/{checkinId}                 檢錄紀錄（id = `${matchId}__${memberId}`）
│
├── matchSheets/{matchSheetId}           出場名單（id = `${matchId}__${teamId}`）
│
├── challenges/{challengeId}             挑戰關卡
│
├── players/{playerId}                   Challenge 玩家（Game Pass）
│
├── attempts/{attemptId}                 挑戰紀錄
│
├── leaderboards/{leaderboardId}         排行榜快取（id = challengeId）
│
├── registrations/{registrationId}       賽前報名申請
│
├── audits/{auditId}                     稽核日誌
│
├── awards/{awardId}                     獎項（含 Mizuno 冠名）
│
└── boards/{boardId}                     彙總看板（現在進行中、今日賽程）
```

**根層級**（跨活動共用）：

```
config/{configKey}                       全站設定（formats、rankingRules、featureFlags）
rolePermissions/{role}                   角色權限對照（沿用 FC 機制）
userPermissionGrants/{uid}               個人權限授予
staff/{uid}                              工作人員名冊與指派
```

### 2.2 為什麼 `matches` 是扁平的

如果放成 `divisions/{d}/stages/{s}/matches/{m}`，「今日全部賽程」就要跨 6 個 division × 2–3 個 stage 做 collection group query，rules 也難寫。扁平化後：

- 「今日賽程」= `where('date','==','2026-10-09').orderBy('kickoffAt')`
- 「A 場地賽程」= `where('venueId','==','venue-a')`
- 「某組別賽程」= `where('divisionId','==','u10')`

以 81 筆文件的量級，扁平是明顯正解。

## 3. 索引設計（`firestore.indexes.json`）

| 集合 | 欄位組合 | 用途 |
|---|---|---|
| `matches` | `date ASC, kickoffAt ASC` | 今日賽程 |
| `matches` | `divisionId ASC, stageId ASC, matchNo ASC` | 組別賽程 |
| `matches` | `venueId ASC, kickoffAt ASC` | 場地賽程 |
| `matches` | `status ASC, kickoffAt ASC` | 進行中／即將開始 |
| `matches` | `teamIds ARRAY, kickoffAt ASC` | 球隊賽程（推薦：`teamIds:[homeId,awayId]`） |
| `timeline` (CG) | `matchId ASC, seq ASC` | 事件流 |
| `timeline` (CG) | `type ASC, playerId ASC` | 射手榜重算 |
| `members` (CG) | `eventId ASC, divisionId ASC, jerseyNo ASC` | 名單 |
| `checkins` | `matchId ASC, teamId ASC, scannedAt ASC` | 檢錄清單 |
| `attempts` | `challengeId ASC, isBest DESC, rawValue DESC` | 排行榜重算（higher） |
| `attempts` | `challengeId ASC, isBest DESC, rawValue ASC` | 排行榜重算（lower） |
| `attempts` | `playerId ASC, createdAt DESC` | 我的成績 |
| `audits` | `entity ASC, entityId ASC, createdAt DESC` | 稽核查詢 |

> **路徑說明**：上表所有集合都是 `events/{eventId}` 的子集合（與 `07` 的 rules、Cloud Functions 觸發路徑一致）。因此**一般複合索引不需要 `eventId` 前綴**——父層路徑已限定範圍；表中標示 `(CG)` 的才是 collection group 索引，此時才需要 `eventId` 欄位做過濾。本次只有單一 Event，實務上可先不建 CG 索引。
>
> **必做**：`matches` 增加冗餘欄位 `teamIds: [homeTeamId, awayTeamId]`，用 `array-contains` 查球隊賽程，避免兩次查詢再合併。

## 4. 命名與編碼慣例（對齊 FC 的 CLAUDE.md）

| 規則 | 內容 | 對應 FC 規則 |
|---|---|---|
| 文件 ID | 一律 `doc(id).set()`，禁止 `add()`（`timeline`／`attempts`／`audits` 例外，允許 `add()`） | R-ID-007 |
| 使用者欄位 | `staff` → `uid`；`checkins` → `scannedBy`；`audits` → `actor.uid` | R-ID-003 |
| 非同步 | 一律 `async/await`，禁止新增 `.then()` 鏈 | R-CODE-001 |
| XSS | 不可信內容（隊名、球員名、暱稱、備註）一律 `escapeHTML()` 或 `textContent` | R-CODE-002 |
| 模組掛載 | `Object.assign(App, { ... })`，禁止新增全域變數 | R-CODE-004 |
| 版本 | `0.YYYYMMDD{suffix}`，只用 `node scripts/bump-version.js` | R-REL-003 |
| Service Worker | 禁止 HTML cache-first；新資源必須由 bump 腳本納管 | R-REL-013/014 |

### 4.1 ID 命名規則

| 類型 | 格式 | 範例 |
|---|---|---|
| Division | 語意小寫連字號 | `u6` `adult-open` `women` |
| Stage | 語意 | `group` `placement` `final` |
| Team | `t-{3碼流水}` | `t-101` |
| Member | `m-{teamNo}-{2碼}` | `m-101-07` |
| Match | `{組別碼}-{階段碼}-{小組}-{序}` | `AO-G-A-01`、`U10-P-SF1` |
| Standing | `{divisionId}__{stageId}__{groupId}` | `adult-open__group__A` |
| Challenge | `g{兩碼}-{語意}` | `g04-speed-king` |
| Player | `FEDA-{4碼}` | `FEDA-0182` |

組別碼：`U6` `U8` `U10` `WM`（女子）`AF`（成人興趣）`AO`（成人公開）
階段碼：`G`（分組）`P`（排名）`F`（決賽）

### 4.2 時間

- 一律存 Firestore `Timestamp`（UTC），前端以 `Asia/Taipei` 顯示。
- `date` 額外存 `'YYYY-MM-DD'` 字串（台北日期），供查詢與分組顯示。
- 比賽時鐘不存「剩餘秒數」，存 `periodStartedAt` + `elapsedSecAtPause`，前端自行推算，避免每秒寫入。

## 5. 資料存取策略

### 5.1 監聽（onSnapshot）用量控制

| 頁面 | 監聽對象 | 數量 |
|---|---|---|
| 首頁 | `boards/live` | 1 |
| 今日賽程 | `matches where date == today` | 1 query |
| LIVE 比賽頁（公開） | `matches/{id}` + `timeline` | 2 |
| LIVE 裁判台 | `matches/{id}` + `timeline` + `matchSheets`×2 | 4 |
| 積分榜 | `standings where divisionId == x` | 1 query |
| 排行榜 | `leaderboards/{challengeId}` | 1 |

> 一般觀眾任一時刻的即時監聽數控制在 **≤ 3**。離開頁面必須 `unsubscribe()`（放進 `js/core/` 的頁面生命週期管理）。

### 5.2 公開投影（Public Projection）

球員文件同時含公開與敏感欄位。兩種做法：

| 做法 | 說明 | 建議 |
|---|---|---|
| A. rules 欄位白名單 | Firestore rules 無法限制「回傳部分欄位」，只能全給或全不給 | ❌ 不可行 |
| B. 雙文件投影 | `members/{id}`（敏感，限賽務）＋ `members/{id}/public/profile`（公開） | 較繁瑣 |
| C. 冗餘公開集合 | `teams/{teamId}/roster/{memberId}` 只放公開欄位，由 Function 同步 | ✅ **採用** |

實作：`onDocumentWritten('events/{e}/teams/{teamId}/members/{memberId}')` → 同步寫入 `teams/{teamId}/roster/{memberId}`。**公開欄位清單以 `01b` §1.6.1 為唯一權威來源**，其他文件不得自行列舉。公開端只讀 `roster`。

```
gs://feda-cup-2026.appspot.com/
├── teams/{teamId}/logo.png                隊徽（≤ 500KB，正方形）

```

規則：上傳一律經前端壓縮（`canvas` resize ≤ 1280px 長邊）再上傳；`storage.rules` 限制 MIME 與大小。

## 7. 資料量估算

| 集合 | 預估文件數 | 說明 |
|---|---|---|
| `matches` | 81 | — |
| `timeline` | ~1,200 | 每場約 15 筆事件 |
| `teams` | 38 | — |
| `members` | ~600 | 每隊 12–18 人 |
| `checkins` | ~2,400 | 每場 2 隊 × 約 15 人 |
| `matchSheets` | 162 | 81 場 × 2 |
| `standings` | ~14 | 各組別各階段 |
| `players` | 200–500 | Challenge 玩家 |
| `attempts` | 800–2,000 | — |
| `audits` | 500–2,000 | — |

**結論**：總文件數 < 10,000，讀取次數估 **50–150 萬次／三日**（含即時監聽）。以 Firestore 免費額度 5 萬讀／日不足，需開 Blaze；估算成本 **NT$100–400**（含 Functions 與流量）。`boards` 扇出設計可把讀取量壓低約 60%。
