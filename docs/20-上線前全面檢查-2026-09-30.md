## 仍需上線前處理的問題

P1 表示會影響比賽結果、資料完整性或存取權限，應在正式賽事前處理。以下除特別註明外是程式審查確認的缺口，尚未新增故障注入或壓力測試，不宣稱已在線上發生。

### P1 重新產生賽程不是不可分割的操作

位置：`js/modules/admin/schedule.js` 的 `generate()`；`js/modules/admin/data.js` 的 `deleteMatches()`、`writeStagesAndGroups()`、`writeStandings()`、`writeTeamGroups()`、`writeMatches()`。

開打限制只檢查瀏覽器當時載入的場次，接著分別刪除場次、寫小組、積分、分組、場次及稽核。若確認對話框期間另一設備開賽，或任一步網路／權限失敗，就可能刪除已開打場次或留下部分重建的資料。

刪場次也沒有清理 `checkins`、`matchSheets` 和 timeline 子集合。檢錄及出場名單可在開賽前存在，而重新產生使用相同場次 ID，舊紀錄可能附到新對戰上；目前「未開賽就沒有舊資料」的前提不足。

修正方向：移到伺服器，以賽程版本和即時狀態守衛執行；同時處理相關紀錄。資料量超出單次交易時需使用新版本建置後切換及可重試的清理流程。在完成前，排程定案後應停止重產，避免多位管理員同時操作。

### P1 晉級寫入與目標場次開賽之間存在競爭

位置：`functions/pipeline.js` 的 `advancementCtx()`、`resolveAdvancementForStage()`。

晉級解算先讀場次和積分，在交易外檢查是否可更新，最後用 batch 寫入。若目標場次在讀取後、提交前開打，或上游比分在此期間改判，原本的檢查無法保護最後的提交，可能把過期隊伍寫進目標場次。

修正方向：在同一交易中讀取並檢查來源及目標版本，重新解算後提交；新增「解算期間開賽」和「兩次改判交錯」整合案例。單元測試中的已開打保護，只能證明傳入快照的判斷正確。

### P1 球隊退賽不會立即更新積分及晉級

位置：`functions/index.js` 的 `onTeamWritten()`；`functions/pipeline.js` 的積分計算使用 `withdrawnIdsOf()`。

當球隊 `withdrawn` 改變，觸發器會重建射手／紅黃牌看板，卻沒有重算所屬小組積分或晉級。引擎本身已有退賽計算，但在下一次相關場次異動以前，公開積分仍可能保留舊結果，已解出的晉級也不會因此重新檢查。

修正方向：將退賽及恢復參賽納入受影響小組與下游的重算流程；同時保護已開打下游場次，回報需人工處理的衝突。

### P1 部分改判成功卻可能沒有稽核紀錄

位置：`js/modules/admin/match.js` 的 `act()` 及申訴、直播設定；`functions/pipeline.js` 的晉級寫入與最終排名發布。

目前結果更新與 `writeAudit()` 是先後兩次提交。如果第一步成功、第二步失敗，結果已變但稽核不存在，前端還可能提示「沒有改判成功」。這與「一切可修正、一切留痕」的要求不一致。

修正方向：業務資料與 before／after／who／when／why 以同一 batch 或交易寫入；需要伺服器運算時由 callable 統一驗權、版本檢查及留痕。補上「稽核寫入被拒絕時結果也不可改變」的故障測試。

### P1 Storage 沒有排除停用人員

位置：`storage.rules` 的 `isStaff()` 和 `members` 原圖規則。

目前只檢查 `staff/{uid}` 文件存在；`active:false` 或已清空 roles 的帳號仍符合條件。只要桶內有檔案，這些帳號仍可能讀球員原圖並寫入圖片。Firestore 的停用保護不會自動套用到 Storage。

修正方向：Storage 同步驗證 active 及允許的角色，依圖片類型設定讀寫邊界，新增 Storage emulator 測試。此次未讀取私密圖片、未驗證線上 Storage 是否已啟用，也未部署 Storage 規則。

### P1 公開名單刪除失敗被忽略及同步競爭

位置：`functions/pipeline.js` 的 `syncRosterFor()`、`recountTeamMembers()`。

當私密名單不存在或不再核准，程式以 `rosterRef.delete().catch(() => {})` 刪除公開投影。它會吞掉所有錯誤，包括服務暫時失敗；此時觸發器可能視為成功，既有公開名單仍會留下。

投影更新及核准人數重算也採先讀後寫，沒有交易或來源版本檢查。較慢的同步可能在新一次刪除／修改完成後，重新寫回舊投影或舊人數。這是來源與衍生資料不同步的風險，並非已證實公開投影會包含生日或身分證欄位；目前欄位白名單測試仍通過。

修正方向：不要吞掉需要重試的刪除錯誤；在同一交易中重讀名單、核對來源版本及更新投影／人數。以延遲讀取、刪除失敗和兩次修改交錯來驗證。

另在目前已關閉的自助報名路徑，`rejectDuplicateApplication()` 沒有重讀目標是否仍為 pending，也沒有決定哪一筆是較早申請；舊建立事件重送或兩筆同時建立時，可能退掉已審核或所有待審申請。再次開放自助報名前應補上交易及確定性排序。

### 套件風險尚未更新

以目前 lockfile 執行 npm audit：根目錄有 20 個受影響的依賴項目，其中 critical 1、high 3、moderate 16；包含 Firebase CLI 開發工具鏈中的 tar、fast-uri、undici。Functions 的正式依賴使用 `--omit=dev` 檢查，為 12 個 moderate，無 high／critical，包含 qs、uuid 及依賴它們的套件鏈。

這些是受影響套件項目數，不能解讀成相同數量的獨立漏洞，也不是已證明本專案可以被利用。部分建議修復涉及 Firebase Admin／Functions／Tools 的主版本升級，本次未直接執行破壞式升級。應另行更新 lockfile、檢查 Node 22 相容性，並重跑全部測試後再部署。npm audit 的範圍是 lockfile；前端從 CDN 固定載入的 Firebase 12.0.0 不等於根目錄測試依賴版本，不在這份 npm 稽核的完整涵蓋範圍內。
